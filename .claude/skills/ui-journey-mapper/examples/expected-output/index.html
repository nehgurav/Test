Developer acceptance scenarios

  1. Search by matching name; verify the result link contains the customer ID.
  2. Search by email with different casing; verify case-insensitive matching.
  3. Submit a query with zero matches; verify SCR-005 and that the input/Search action remain available.
  4. Search again from SCR-005 with a matching query; verify return to SCR-001.
  5. Open a known ID directly and verify SCR-002; open an unknown ID and verify SCR-003 on the same route pattern.
  6. Choose Edit; verify the edit form is an in-place state change.
  7. Try empty name or malformed email; verify browser-native validation blocks submission.
  8. Save valid values; verify the in-memory value and saved status change. Refresh and confirm that persistence is not implemented.
  9. Cancel a draft; verify existing customer values remain unchanged.
  10. Verify shared action ACT-006 appears in both SCR-002 and SCR-003 and returns to /customers.

These are recommended test cases derived from source behaviour—not execution results.

Architect review · unknown or absent capabilities

This source sample contains no backend API boundary. Do not invent an API, database, identity provider, audit trail, or deployment topology in generated documentation.
  • API ownership, endpoint contract, schemas, timeouts, retries, and error mapping.
  • Authentication, authorization, session/token handling, and route/data access controls.
  • Persistence, transaction/concurrency strategy, and update-conflict handling.
  • Auditability, sensitive-field exposure, data retention, and privacy controls.
  • Observability: correlation IDs, structured logs, metrics, traces, and alerting.
  • Deployment/runtime boundaries, environment configuration, service dependencies, and resilience behaviour.

On a real repository, inspect API specifications, API clients, service implementations, deployment configuration, infrastructure manifests, and runtime evidence before making architecture claims.
